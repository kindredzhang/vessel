vessel · 前端说明

同一股流，两条路线

运行时只吐一种东西：SSE 帧。界面上那两个开关（assistant-ui adapter / AI SDK transport）不是两种后端， 而是把这同一股流翻译成两种内部表示。下面把一次真实回合拆成 12 步，逐帧看两边各自多出了什么。

决定 · 2026-11-19

只保留路线 B · AI SDK transport。路线 A 的代码（chat/localRuntime.tsx）已删除； 这一页留作取舍的记录，下面的 12 步仍然完整说明两条路线的差别 —— 只是其中一条已经是历史。

01 · 先把三个词分开

SSE、part、chunk

SSE —— 传输格式

服务器一次连接、单向、按帧推送的纯文本。我们的运行时用它把「模型说了一个字」「工具开跑了」这类事件即时送给界面。

帧的语法固定：event: 名字 → data: 一行 JSON → 空行结束。

part —— 消息的内容单元

assistant-ui 把「一条助手消息」表示成一个 part 数组：text、reasoning、tool-call。渲染时逐个 part 换组件。

关键：adapter 路线每次 yield 整条消息的完整快照，不是增量。

chunk —— 协议的增量

AI SDK 用一串 UIMessageChunk 描述同一条消息：text-start → 很多 text-delta → text-end，工具则是 tool-input-* / tool-output-*。

关键：chunk 是增量，由 AI SDK 自己累积成 UIMessage。

我们运行时真正发出的东西

event: text
data: {"delta":"我先看一下这个目录。"}

event: tool
data: {"phase":"start","name":"bash","summary":"ls src/vessel/access"}

event: approval
data: {"toolName":"bash","risk":"unknown","description":"ls src/vessel/access"}

event: done
data: {"accessMode":"ask"}

这四种帧就是全部。两个前端库都不认识它们 —— 认识它们的是我们自己写的适配层。

02 · 两条路线

谁把帧变成消息

路线 A · assistant-ui adapter

我们写一个 ChatModelAdapter，它是个 async generator：每收到一帧就 yield 一次完整快照，assistant-ui 直接用它替换当前助手消息。

消息状态归 assistant-ui；我们负责产出快照。

路线 B · AI SDK transport

我们写一个 ChatTransport：把每帧翻成 1～2 个 UIMessageChunk 塞进 ReadableStream。AI SDK 自己累积成 UIMessage[]。

消息状态归 AI SDK；我们只负责协议翻译。

两条路都不管的：审批

approval 帧不是模型输出，两边都没有对应类型。所以我们用一条旁路（TurnChannel 信号）把它递给界面，用户点完再 POST /approvals。

这就是为什么两边的审批体验一模一样。

04 · 差异表

所以到底差在哪

路线 A · assistant-ui adapter路线 B · AI SDK transport
谁维护消息 assistant-ui 的 runtime；我们把整条消息重算后交给它 AI SDK；我们只交 chunk，它自己拼
数据形状 快照（幂等：给同样输入，结果一样） 增量（有序：少一个 delta 就少一个字）
我们写的代码 一个 generator，约 60 行，逐事件重算 parts 一个 transport，约 90 行，逐帧翻译 chunk
工具调用 tool-call part，带 argsText 和 result tool-input-available + tool-output-available chunk，AI SDK 合成 tool-* part
审批 旁路信号（不进消息） 旁路信号（协议里没有这类 chunk）
断线续传 自己做（重放快照很自然：再算一遍就行） reconnectToStream() 是协议一等公民
附加能力 就是 assistant-ui 本身：primitives、分支、编辑重发 AI SDK 生态：持久化适配、telemetry、useChat 语义
体积 跟主包一起（无额外依赖） 独立 chunk 310 kB / gzip 86 kB，lazy() 按需加载
出问题时 快照错 → 整条消息错，但容易复现 chunk 错 → 拼出来的消息错，要看序列
05 · 代码

两边真正的入口长什么样

路线 A · adapter 
// chat/localRuntime.tsx —— 每次 yield 都是完整快照
async *run({ abortSignal }) {
  const parts = [];
  for await (const event of channel.turn(text, abortSignal)) {
    if (event.type === "text") {
      cursor = pushText(parts, cursor, event.delta);
    }
    if (event.type === "tool") {
      pushTool(parts, event);   // 工具后文字另起一段
      cursor = parts.length;
    }
    yield { content: [...parts] };   // ← 整条重发
  }
}
路线 B · transport 
// chat/wireRuntime.tsx —— 只发增量
async sendMessages({ messages, abortSignal }) {
  return new ReadableStream({
    async start(controller) {
      for await (const event of channel.turn(...)) {
        if (event.type === "text")
          send({ type: "text-delta", id: textId, delta: event.delta });
        if (event.type === "tool" && event.phase === "start")
          send({ type: "tool-input-available", toolCallId, toolName, input });
        // 谁累积？AI SDK。我们只翻译。
      }
    }
  });
}

一句话总结：A 是「我把整条消息重算给你」，B 是「我把新内容按协议告诉你，你自己拼」。 前者更简单、更好重放；后者换来 AI SDK 生态和它对流式协议的既有处理。
